# Synthetic Patient Data Retrieval

A Streamlit app for asking questions over **synthetic** patient records. Synthea generates FHIR Bundles; `loadGeneratorData.py` loads them into SQLite; retrieval is being built as a hybrid RAG pipeline over that same database.

```powershell
uv run streamlit run src/synthetic_patient_data_retrival/app.py
```



## Why not PDF-style RAG?

The notebook on `notebook-intro` used Document Loader → chunk → embed → Chroma cosine search. That works when each chunk is a self-contained paragraph.

The medical data generated by Synthea is relational with various indentifiers. Since the data/observations can be represented with different text with the same semantic meaning, and data is spread across the relational database. So cosine similarity will not be accurate because
1. **Vocabulary mismatch** — the query and the row do not share tokens, even when they mean the same thing.
2. **Missing identifiers** — the matched row does not contain enough of the patient/encounter identity for the model to answer.



## Why sqlite-vec + FTS5 (not Chroma)

The source of truth is already `data/sqlite/patient.db`. Adding Chroma would duplicate facts into a second store and make every hit a second lookup to recover `patient_id` / `encounter_id`.

Keeping search inside SQLite means one file and one query surface:

| Layer | Tool | What it is for |
| --- | --- | --- |
| Structured filters | SQL `WHERE` | Patient, date range, resource type |
| Keyword / codes | FTS5 (BM25) | Names, drug names, ICD/SNOMED/RxNorm codes |
| Paraphrase / synonyms | sqlite-vec `vec0` KNN | `high blood pressure` ≈ `hypertension` |
| Merge | Reciprocal Rank Fusion (RRF) | Rank items that hit both lists higher |
| Context for the LLM | `JOIN` back to patients/encounters | Fill in the 8/10 identifiers the chunk lacked |

`sqlite-vec` default KNN is brute-force exact search. That is the right default for a local Synthea database: correct neighbors, simple, fast enough. Partition keys can speed filtered KNN, but should stay coarse (`resource_type` or month), not one partition per patient, unless each patient has hundreds of vectors.

Chroma stays in `notebooks_archive/` as the tutorial path. It is the wrong home for data already modeled with foreign keys.

Caveats: sqlite-vec is pre-v1 (APIs can change). Load it as an extension (`pip install sqlite-vec`, then `sqlite_vec.load(conn)`). FTS5 is built into SQLite.

### Additional Notes
If content_length is too short, additional keys are added to provide the encoder with more semantic context
Not chunking langchain documents since average length is approx~ 54, and max 167 characters when tested

## Retrieval units

Do not split raw rows with `RecursiveCharacterTextSplitter`. Index two kinds of text:

**Encounter documents** (primary). Denormalize identity and clinical facts so a vector can match a multi-fact query:

```text
Patient: Jane Doe, female, DOB 1962-03-14, patient_id=abc
Encounter: 2019-06-02, Wellness, encounter_id=xyz
Conditions: Essential hypertension (I10); Type 2 diabetes (E11)
Medications: Lisinopril 10mg; Metformin 500mg
Observations: Systolic BP 142 mmHg; HbA1c 7.4 %
```

**Row-level chunks** (pointers). One condition, observation, medication, or procedure, with `patient_id`, `encounter_id`, `resource_type`, and `code` in metadata. FTS5 text should include aliases (`hypertension HTN I10 high blood pressure`).

Query flow:

1. Extract filters from the question (name, dates, resource type) → SQL `WHERE`.
2. Hybrid search (FTS5 + vec0 KNN + RRF) inside that candidate set.
3. JOIN the hit back to the full patient/encounter document before sending context to the LLM.

`all-MiniLM-L6-v2` (384-d) is enough to start. A biomedical embedding later helps synonyms more than switching vector databases would.

## Data pipeline

1. Synthea (`data/generator/synthea-with-dependencies.jar`) writes FHIR Bundles to `data/generator/output/fhir/`.
2. `PatientDatabaseManager` parses Patient, Encounter, Condition, Observation, MedicationRequest, and Procedure resources into SQLite tables, plus `rag_audit`.
3. `rag_retrival.py` currently converts each table row into a LangChain `Document` (sparse `page_content` + ID metadata). Chroma embed/query code is still the leftover skeleton.
4. `app.py` is the Streamlit form; it is not wired to retrieval yet.

`data/` is gitignored and cursorignored. Recreate `patient.db` with `loadGeneratorData.py`. Do not commit the Synthea JAR output or the SQLite file.
